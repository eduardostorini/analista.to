What is SPF?

SPF (Sender Policy Framework) is an email authentication standard that allows the owner of a domain to publish, via a TXT record, a list of servers authorized to send email on their behalf. When an email server receives a message, it can query the SPF of the sending domain to verify whether the source server is on the authorized list — if not, the message may be marked as suspicious, moved to spam, or rejected, depending on the recipient's policy. The {{ site_name }} SPF Checker locates the SPF record for the domain, decomposes its mechanisms, and calculates how many additional DNS queries that record requires — a frequently overlooked technical detail, capable of invalidating the entire SPF if it exceeds the protocol limit.

How to interpret the result

RFC 7208 defines a strict limit of 10 DNS queries for evaluating an SPF record (counting mechanisms like a, mx, include, exists, redirect and ptr — mechanisms like ip4 and ip6 do not count, as they do not require an additional query). If this limit is exceeded, receiving servers should treat the result as permerror, which in practice invalidates SPF protection — it is a common error in domains that accumulate multiple email services via include: over time without review. The qualifier of the final all mechanism defines what to do with unlisted senders: -all (fail) rejects, ~all (softfail) marks as suspicious but generally accepts, ?all (neutral) defines no policy, and +all (pass) authorizes any server — a dangerous configuration that practically nullifies the purpose of SPF.

Common use cases

This tool is essential when adding a new transactional or marketing email provider (such as a newsletter sending service) to a domain's email infrastructure — each new include: added brings the record closer to the 10-lookup limit. It is also used to diagnose why legitimate emails are landing in spam (an absent, misconfigured, or +all SPF increases the chance of this), and to periodically audit SPF records accumulated over years, removing includes from unused services.

Limitations

This tool calculates the lookup count at the top level of the record, but include: mechanisms can, in turn, point to other SPF records that also consume additional lookups in a cascade — a complete analysis would require resolving each include recursively, which can be done manually by combining the result of this tool with TXT Lookup for each included domain. SPF alone also does not guarantee deliverability — it works best in combination with DKIM and a well-configured DMARC policy.

SPF alone is not enough

A common conceptual error is treating SPF as complete protection against email spoofing. In practice, SPF validates only the server that sent the message (the technical "envelope from"), not the address that appears visually to the recipient in the "From" field. It is perfectly possible for a malicious sender to send a message that passes SPF on a different domain than the one shown in the visible header to the user — this is exactly the scenario that DMARC was created to close, requiring alignment between the authenticated domain and the displayed domain. For this reason, industry best practice is always to implement SPF, DKIM, and DMARC together, never one in isolation.
