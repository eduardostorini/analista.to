What is the HTTP 2/3 Checker?

HTTP/2 and HTTP/3 are newer versions of the protocol that powers the web, designed to replace the older, request-at-a-time model of HTTP/1.1 with faster, more efficient ways of moving data between browser and server. This tool connects to a domain the same way a browser would, negotiates the connection over TLS, and reports which protocol version the server actually used, together with whether it advertises HTTP/3 (QUIC) support through the standard Alt-Svc response header — the same signal real browsers rely on to decide whether to upgrade a future connection to HTTP/3.

How to interpret the result

"HTTP/2 supported" means the TLS handshake's ALPN negotiation — the mechanism client and server use to agree on a protocol before any HTTP traffic is exchanged — selected HTTP/2 for this connection, which in practice requires HTTPS; plain HTTP almost never upgrades to HTTP/2 in the real world, so testing over an unencrypted connection will normally show HTTP/1.1 even on servers that fully support HTTP/2 over TLS. "HTTP/3 (QUIC) advertised" reflects the presence of an h3 token in the Alt-Svc header, which is how a server tells clients "I also speak HTTP/3 on this port, feel free to try it next time" — it does not mean this particular request traveled over HTTP/3, since QUIC runs over UDP and requires a separate connection attempt that browsers make opportunistically after seeing this header.

Why the protocol version matters

HTTP/1.1 opens a limited number of parallel connections and processes requests on each one mostly in sequence, which is why old-school sites split assets across multiple domains to work around the limit. HTTP/2 introduced multiplexing — many requests and responses interleaved over a single connection — plus header compression and server push, cutting page load times considerably on sites with many small resources. HTTP/3 goes further by replacing the underlying TCP transport with QUIC, built on UDP, which removes a problem called "head-of-line blocking" (where one lost packet stalls every request sharing that TCP connection) and speeds up connection setup, which is especially noticeable on mobile networks with higher latency and packet loss.

Common use cases

Site owners use this tool to confirm that a CDN or reverse proxy migration actually enabled HTTP/2 or HTTP/3 as expected, since it is easy to assume a modern CDN provider turns these on by default when in fact a specific configuration flag was left disabled. Developers use it while debugging performance regressions, since dropping from HTTP/2 back to HTTP/1.1 — for example after switching load balancers — can silently increase load times without any error being raised anywhere. It is also useful for competitive research, checking which protocol a competitor's infrastructure uses, and for basic due diligence when choosing between hosting providers or CDNs that advertise HTTP/3 support.

Limitations

This tool does not open a raw QUIC/UDP connection to verify HTTP/3 directly — doing so reliably from a server-side background job is significantly more involved than a normal HTTP request, and is not how most lightweight online checkers work either. Instead, it relies on the Alt-Svc header, the same well-established mechanism browsers use, which is accurate for any server that correctly advertises its capabilities but will miss a misconfigured server that supports HTTP/3 without announcing it. Results can also vary by region for sites behind a CDN with per-datacenter configuration, and a server may temporarily disable HTTP/2 or HTTP/3 under specific load conditions.
