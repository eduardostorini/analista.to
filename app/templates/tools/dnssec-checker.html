What is DNSSEC?

DNSSEC (Domain Name System Security Extensions) is a set of extensions to the standard DNS protocol that adds cryptographic signatures to DNS responses, allowing a resolver to verify that the answer it received for a query really came from the domain's authoritative nameservers and was not altered or forged in transit. Ordinary DNS has no built-in authenticity mechanism: any party positioned between a resolver and the internet — a compromised network, a rogue Wi-Fi hotspot, an attacker performing DNS cache poisoning — can, in principle, inject a forged response that points a domain to the wrong IP address, redirecting traffic to a malicious server without the user noticing. DNSSEC closes this gap by having the domain's zone owner sign its records with a private key and publish the corresponding public key (and a fingerprint of that key, called a DS record, at the parent zone) so any resolver can verify the signature and build a cryptographic chain of trust from the DNS root all the way down to the specific record being queried.

How to interpret the result

This tool checks for the presence of DNSKEY records (the public keys published by the zone) and DS records (the fingerprint of those keys published by the parent zone, which links the domain into the chain of trust). If no DNSKEY records exist, the domain simply does not have DNSSEC enabled — a common and, for most domains, acceptable state. If DNSKEY records exist but no DS record is found, the domain is signing its own records but the parent zone has not been told to trust that signature, which means most validating resolvers will treat the domain as if DNSSEC were not enabled at all — this is a classic misconfiguration that occurs when DNSSEC is enabled at the DNS provider but the resulting DS record was never submitted to the domain registrar. The tool also performs a live query with the EDNS "DO" (DNSSEC OK) bit set and checks whether the resolver's response carries the AD (Authenticated Data) flag, which is the resolver's own confirmation that it successfully validated the signature chain for that query.

Common use cases

System administrators use this tool right after enabling DNSSEC at their DNS provider to confirm the DS record has been correctly submitted to the registrar and is visible in the chain of trust, since a missing or mismatched DS record silently disables the protection while giving no error to the person who enabled it. Security teams use it during vendor and third-party domain audits to check whether partners or acquired domains have DNSSEC properly configured, particularly for domains used in financial services, government, or other high-assurance contexts where DNS spoofing protection is a compliance requirement. It is also useful when diagnosing DNS resolution failures that only affect DNSSEC-validating resolvers (such as those provided by some ISPs and public DNS services) — a broken DNSSEC chain, rather than a plain missing record, can cause a domain to resolve correctly on some networks and fail entirely (SERVFAIL) on others.

Limitations

The AD flag check depends on the recursive resolver used for the query actually performing DNSSEC validation itself; if that resolver does not validate DNSSEC at all, the AD flag will never be set even for a domain with a perfectly intact chain, which this tool reports as "undetermined" rather than a false failure. This tool does not verify the cryptographic signatures byte-by-byte the way a full validating resolver does — it reports the presence of the expected records and the resolver's own validation flag as strong signals, which is sufficient for the vast majority of diagnostic purposes but is not a substitute for a dedicated DNSSEC analyzer when investigating a subtle signing bug. It also does not check for specific algorithm deprecations or key rollover timing issues, which require inspecting signature validity windows over time rather than a single point-in-time query.

Why most domains still don't use DNSSEC

Despite being standardized for over two decades, DNSSEC adoption remains uneven across the internet, largely because it adds operational complexity: keys must be rotated periodically, the DS record must be kept in sync between the DNS provider and the registrar whenever keys change, and a misconfiguration can take an entire domain offline for every DNSSEC-validating resolver in the world, which is a much more severe failure mode than an unsigned domain simply lacking the protection. Domains that handle sensitive transactions, government services, or that are frequent targets of DNS spoofing and cache-poisoning attacks generally benefit the most from enabling it, while the operational risk of a misconfigured chain of trust is the main reason many domain owners choose to leave it disabled or delay adoption.
