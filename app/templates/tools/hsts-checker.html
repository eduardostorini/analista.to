What is HSTS?

HTTP Strict Transport Security (HSTS) is a response header, defined in RFC 6797, that instructs a browser to only ever contact a domain over HTTPS for a specified period of time — even if the user types a plain http:// address, clicks an old bookmarked link, or follows a link from an insecure page. Without HSTS, that first request still goes out over plain HTTP before any redirect can happen, leaving a brief but real window in which a network attacker positioned between the user and the server (for example, on public Wi-Fi) can intercept or downgrade the connection before HTTPS is ever established. This tool fetches the domain over HTTPS, reads the Strict-Transport-Security header it returns, and breaks down its directives so you can confirm the policy is actually configured the way you intend.

How to interpret the result

The max-age directive, in seconds, tells the browser how long to remember to enforce HTTPS-only for this domain after the current visit — a short value re-exposes users to the downgrade window sooner, which is why a duration of at least six months, and ideally a full year, is recommended. includeSubDomains extends that same enforcement to every subdomain of the site, which matters because an attacker who can get a victim to visit even one insecure subdomain could otherwise still intercept cookies scoped to the parent domain. The preload directive is a signal of intent to be included in browser preload lists (see below) but, by itself, does nothing — inclusion requires a separate manual submission and review process.

Common use cases

This tool is used to confirm that HSTS was actually deployed correctly after a configuration change, to audit third-party or partner domains before a security review, and to diagnose why a domain still appears vulnerable to protocol-downgrade findings in a penetration test report despite HTTPS being available. It is also a useful first step before considering submission to the official HSTS preload list, since the list's minimum technical bar (a long max-age, includeSubDomains, and the preload directive, all served correctly on the apex domain) can be checked here first.

Limitations

The "heuristically preload-eligible" indicator in this report checks only the syntactic conditions publicly documented for preload list submission — it does not query the real hstspreload.org list, does not verify that every subdomain actually serves a valid HTTPS certificate (a hard requirement for real submission), and does not guarantee acceptance. Treat it strictly as a starting-point signal, and always verify current eligibility directly on hstspreload.org before submitting a domain, since browsers ship the real preload list independently of what any third-party tool reports.

The HSTS preload list

Even a long max-age does not protect the very first connection a browser ever makes to a domain it has never visited before — that first request is inherently unprotected because the browser has no prior HSTS policy stored for it yet. The preload list solves this "trust on first use" gap: major browsers ship a hardcoded list of domains, maintained by Google and used by Chrome, Firefox, Safari, and Edge, for which HTTPS is enforced from the very first connection, before any header is ever received. Submission is done manually at hstspreload.org and requires the domain (and, per the includeSubDomains requirement, every subdomain) to serve a valid certificate — a decision that is difficult to reverse quickly, since removal from the list can take months to propagate through browser release cycles.

Rolling out HSTS safely

Because HSTS is remembered by the browser for the full max-age duration, a mistake made while HTTPS is not yet fully reliable across every subdomain can lock out real users until the policy expires. The safe rollout pattern is to start with a short max-age (for example, a few minutes to hours) while confirming every subdomain in scope serves valid HTTPS, then progressively increase it toward the one-year value recommended for preload eligibility, only adding includeSubDomains once every subdomain has been verified.
