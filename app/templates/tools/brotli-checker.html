What is the Brotli Checker?

Brotli is a compression algorithm created by Google that typically shrinks text-based web content — HTML, CSS, JavaScript, JSON — noticeably more than the older, more common gzip algorithm, without costing extra decompression time in the browser. This tool sends a request to the domain you provide, explicitly telling the server "I can accept Brotli" through the standard Accept-Encoding request header, and then reports which compression algorithm the server actually chose to use in its response. It also repeats the request without offering Brotli, to show what the server falls back to, and checks whether the response correctly includes Vary: Accept-Encoding, a detail that matters more than it might seem.

How to interpret the result

"Brotli supported" means the server returned a response with Content-Encoding: br when we explicitly advertised support for it — a strong, direct signal, not a guess based on the server's name or technology stack. If the encoding shown for the Brotli-offered request is "gzip" or "deflate" instead, it means the server is capable of compression but either does not have Brotli enabled, or has it enabled only for specific content types or paths that this particular page does not match. A result of "none" for both attempts usually means the response body is too small to be worth compressing, is already a compressed format (like an image or a video), or the server has compression disabled entirely. The Vary header check matters for correctness: if a shared cache or CDN stores a Brotli-compressed response and later serves it to a client that only accepts gzip, without Vary: Accept-Encoding telling the cache to key responses by encoding, the wrong clients can end up receiving content they cannot decode.

Why Brotli matters for performance

Smaller responses transfer faster, which directly improves page load times, especially on slower mobile connections where bandwidth is the bottleneck rather than server processing power. Brotli typically achieves compression ratios around 15-25% better than gzip on typical HTML, CSS, and JavaScript, thanks to a larger built-in dictionary tuned specifically for web content and a more sophisticated compression scheme. Because nearly every modern browser supports Brotli decoding, and decompressing it costs about the same as gzip on the client side, enabling it is one of the few web performance wins that costs virtually nothing once configured — the main investment is slightly higher CPU usage on the server when compressing dynamically, which most sites offset by pre-compressing static assets at build time instead of on every request.

Common use cases

Site owners and developers use this tool to confirm that a CDN, reverse proxy, or origin server configuration change actually enabled Brotli as intended, since it is a common assumption that a modern hosting stack has it on by default when a specific module or directive was never actually turned on. Performance audits use it alongside cache-header and HTTP version checks to build a complete picture of a site's delivery optimization. It is also useful when comparing infrastructure between your own site and a competitor's, or when validating that a migration between hosting providers did not silently regress compression settings that were previously fine-tuned.

Limitations

This check reflects a single request to the site's root URL; some servers apply different compression rules to different paths, file types, or response sizes, so a different page on the same site could behave differently. Very small responses are frequently left uncompressed by design, since the overhead of compression can outweigh the savings below a certain size threshold, which is normal and not a misconfiguration. Finally, a small minority of corporate proxies or older intermediaries occasionally strip or rewrite compression-related headers in transit, which could make a Brotli-enabled origin server appear otherwise when tested from certain networks.
