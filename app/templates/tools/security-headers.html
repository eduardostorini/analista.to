What are HTTP security headers?

In addition to controlling cache and content type, HTTP headers can also instruct the browser to apply additional security policies — such as refusing to load the page inside an <iframe> of another site, preventing the browser from insecurely "guessing" the type of a file, or restricting which domains scripts and styles can be loaded from. This tool checks the presence and value of seven widely recommended security headers and calculates a simple score based on how many are present.

How to interpret the result

Two headers are marked as critical: Strict-Transport-Security (HSTS), which instructs the browser to always use HTTPS with that domain, even when the user types or clicks on an http:// link, preventing downgrade attacks; and the Content-Security-Policy (CSP), which restricts which origins the browser can load scripts, styles, and other resources from, being one of the most effective defenses against Cross-Site Scripting (XSS) attacks. The remaining headers — X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy and Cross-Origin-Opener-Policy — reduce more specific risks (MIME sniffing, clickjacking, navigation data leakage, unauthorized access to browser APIs, and tab isolation). The score is a simple sum of presence, not an evaluation of the quality of the configured policy — a present CSP that is configured overly permissively still counts as "present" in this analysis.

Common use cases

Security and development teams use this tool as a quick checklist before a launch, to confirm that security configurations made on the server, CDN, or hosting platform have actually been applied in production. It is also useful in compliance audits and in quick comparisons between the security posture of different environments (production vs. staging) or of vendors during a technical evaluation process.

Limitations

This tool checks only presence and raw value of headers — it does not evaluate whether a CSP policy is well constructed (e.g., whether it uses unsafe-inline insecurely) nor simulate real attacks. The absence of a non-critical header does not necessarily mean a severe vulnerability — it depends on the context and nature of the application. Treat the score as an indicator of basic configuration hygiene, not as a complete security audit.

From theory to practice

Implementing these headers is usually simple from a technical standpoint — most modern web servers, CDNs, and frameworks allow configuring them with a few lines — but requires special attention to the Content-Security-Policy, which can break page functionality if set too restrictively without considering all the script, style, and image domains actually used by the site. A recommended approach is to deploy the CSP first in report-only mode (Content-Security-Policy-Report-Only), which logs violations without blocking anything, allowing the policy to be adjusted safely before activating it in real blocking mode. The other headers on this list have a much lower risk of breakage and can generally be activated directly without that additional care.

Where to configure

Depending on your infrastructure, these headers can be defined at different layers: directly in the application (modern web frameworks often have ready-made extensions for this), on the web server (Nginx and Apache accept simple add_header directives), or on the CDN/reverse proxy in front of the application, which is frequently the most centralized and easy-to-maintain point for all traffic of a domain. When multiple layers define the same header with different values, normally the value defined in the layer closest to the client prevails, so it is worth reviewing the entire chain if an expected value is not appearing correctly in this tool's result.
