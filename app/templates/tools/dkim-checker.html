What is DKIM?

DKIM (DomainKeys Identified Mail) is an email authentication standard that lets a domain cryptographically sign outgoing messages, so that a receiving server can verify the message left the domain's sending infrastructure unmodified and was not forged. Unlike SPF, which authorizes servers by IP address, DKIM works by having the sending server attach a digital signature (in a DKIM-Signature header) computed over parts of the message using a private key; the receiving server then fetches the corresponding public key from DNS, at <selector>._domainkey.<domain>, and verifies the signature against it. The "selector" is simply a label chosen by whoever configured DKIM for the domain — a domain can publish multiple selectors at once, for example one per email service it uses, and rotate keys by publishing a new selector without disrupting mail signed under the old one. This tool fetches the public key TXT record for a specific domain and selector pair and reports the key's type, size and validity.

How to interpret the result

A healthy result shows a public key (the p= tag) that successfully decodes as an RSA or Ed25519 key of adequate size — 2048-bit RSA is the current common baseline, and anything below 1024 bits is flagged as weak, since it falls short of modern cryptographic recommendations and is increasingly rejected or discounted by major receivers. An empty p= tag is a deliberate and valid DKIM state: it means the selector has been revoked, typically because the key was rotated or a mail service was decommissioned, and any message claiming that selector should now fail verification. A missing record entirely (no TXT record found at that name) most often means the selector you entered is wrong rather than that DKIM is unconfigured — selectors are provider-specific and not standardized, so double-check the exact selector your provider uses before concluding DKIM is absent.

Common use cases

This tool is used whenever you need to confirm a specific DKIM selector is correctly published, most commonly right after configuring a new transactional or marketing email service and adding its recommended DNS records — a typo in the selector or an incomplete copy-paste of a long base64 public key are both common setup mistakes this check catches immediately. It is also used during key rotation, to confirm a new selector is live and resolvable before switching the sending infrastructure over to sign with it, and while auditing an inherited domain's email setup, to catalog which selectors are still active versus revoked but potentially forgotten in signing configuration elsewhere.

Limitations

Because DKIM selectors are not discoverable by DNS alone — there is no record that lists "all selectors used by this domain" — this tool can only check one selector you already know, typically found in the DKIM-Signature header of a message the domain actually sent (look for the s= tag) or in your email provider's own setup documentation. It also validates the key's structure and size but does not verify an actual message signature — that requires the full signed message and is better suited to the Email Header Analyzer, which can parse the signature-related headers of a specific message alongside its Authentication-Results verdict.

DKIM alone does not prevent spoofing

A valid DKIM signature only proves the signed content was not altered and was signed by the domain that owns the matching private key — it does not, by itself, guarantee the message's visible "From" address matches the signing domain, since a message can carry a valid DKIM signature from one domain while displaying an entirely different address to the recipient. That alignment check is exactly what DMARC adds on top of DKIM (and SPF), which is why the three are meant to be deployed together rather than DKIM being treated as sufficient authentication on its own.
