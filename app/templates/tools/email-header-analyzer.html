What is the Email Header Analyzer?

Every email carries, beneath the subject and body a person normally sees, a stack of technical headers written by every mail server the message passed through on its way from sender to recipient — most importantly a chain of Received headers (one added by each hop, newest on top) and, when the receiving server checked authentication, an Authentication-Results header summarizing the SPF, DKIM and DMARC verdicts it computed. This tool takes that raw header block, which you paste in after copying it from your email client's "Show original" or "View source" option, and parses it entirely on our server with no network calls of any kind — it reads only what is already written in the text you provide, reconstructing the hop-by-hop delivery path with per-hop timing and summarizing the authentication verdicts into a single overall status, so you don't have to read dense, multi-line header text by hand.

How to interpret the result

The delivery path is listed most-recent-hop-first, matching how Received headers are actually written (each server prepends its own line, so the top line was added last, closest to final delivery). The delay shown on each hop is the time elapsed since the previous, chronologically earlier hop — a long delay on one hop, compared to the others, often points to where a message got stuck, whether due to greylisting, a queue backlog, or a slow spam-filtering step. The overall authentication status is pass when every mechanism found across all Authentication-Results headers reported pass, fail when any of SPF, DKIM or DMARC explicitly failed (worth treating as a signal of possible spoofing), mixed when results disagree without an outright failure, and unknown when no Authentication-Results header was present at all — which happens when the receiving server did not perform or record the check, not necessarily when authentication was skipped entirely.

Common use cases

This tool is most often used to investigate a suspected phishing or spoofing attempt, checking whether SPF/DKIM/DMARC actually failed on a suspicious message rather than relying on the visible From address alone, which is trivial to forge. It is also used to debug deliverability problems — comparing hop timestamps to spot an unexpectedly slow relay, or confirming that a transactional email service is signing with the selector and domain you expect — and to audit a message's full routing path when investigating a security incident, since the chain of Received headers records every server the message actually touched, including ones that never appear in any visible field.

Limitations

Header extraction here is intentionally lightweight, using pattern matching rather than a full formal grammar of every mail transfer agent's header dialect, so unusual or heavily-customized Received header formats may not yield a host or timestamp even when a human could read one out manually — timestamps in particular are best-effort and may be missing on headers that omit a trailing date. This tool also never performs any cryptographic verification itself; it reports whatever verdict the receiving server already recorded in Authentication-Results, it does not recompute or independently confirm an SPF, DKIM or DMARC result. For that, use the dedicated SPF Checker, DKIM Checker and DMARC Checker tools against the sending domain directly.

Privacy of pasted content

Email headers routinely contain real IP addresses, internal hostnames, and genuine email addresses belonging to real people — information that should never be published or listed publicly just because someone ran a diagnostic check on it. For that reason, unlike most other tools on this site, results from the Email Header Analyzer are never turned into a public result page and never appear in any "recent searches" listing; only you can see the output of your own analysis, and it expires from short-term cache like any other result.
