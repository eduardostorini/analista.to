What is schema markup?

Schema markup, most commonly implemented today as JSON-LD (JavaScript Object Notation for Linked Data), is structured data embedded in a page's HTML via a <script type="application/ld+json"> block, following the shared vocabulary defined at schema.org. Instead of forcing a search engine to infer what a page is about purely from visible text and layout, structured data explicitly labels the page's content — this is a "Product" with this name, this price, and this availability; this is an "Article" with this headline, this author, and this publish date; this is a list of "FAQPage" questions and answers. Search engines use this explicit data to power rich results in search listings — star ratings, prices, breadcrumb trails, FAQ dropdowns, event dates — and increasingly as a machine-readable summary of the page for other purposes. The {{ site_name }} Schema Markup Checker fetches the submitted page, locates every JSON-LD block (including items nested inside an @graph array), validates that each one is syntactically correct JSON, and performs a light check for fields commonly expected on well-known schema.org types.

How to interpret the result

Each row in the result table corresponds to one <script type="application/ld+json"> block found on the page. A block marked invalid failed to parse as JSON at all — this is a hard error, usually caused by a missing comma, an unescaped quote, or a templating bug that concatenated broken values into the block, and it means search engines will likely ignore that entire block. A block marked valid is syntactically correct JSON, and the tool lists every @type it declares. For a handful of common types — Organization, LocalBusiness, Product, Article, and FAQPage — the tool also checks for fields that are typically expected for that type to be useful (for example, an Article missing headline, author, or datePublished). These are shown as warnings, not errors: they do not mean the JSON-LD is broken, only that it may be incomplete relative to common practice and to what search engines look for when deciding whether to grant a rich result.

Common use cases

E-commerce teams use this tool to verify that Product schema is correctly emitted on every product page template, since a missing offers or review field can be the difference between showing a price and star rating directly in search results or not. Publishers use it to confirm that Article schema carries a proper headline, author, and datePublished, which search engines use for news and top-stories placements. Local businesses use it to check LocalBusiness or Organization markup for the name, URL, and contact details that feed knowledge panels. It is also a routine step after a CMS migration or template redesign, since structured data is often generated by a specific plugin or code path that can silently break — producing malformed JSON — without any visible symptom on the rendered page itself.

Limitations

This tool checks JSON syntax validity and a small, deliberately limited set of recommended fields for a handful of common types; it is not a full replacement for schema.org's own validation or Google's Rich Results Test, which check hundreds of type-specific requirements and simulate exactly which rich result (if any) a given page qualifies for. A block can be syntactically valid JSON-LD, and pass every check this tool performs, and still fail to earn a rich result because of type-specific requirements this tool does not check, content-quality guidelines, or values that do not match the actual visible content of the page — search engines penalize structured data that misrepresents what a user actually sees. This tool also only reads JSON-LD; some sites use the older Microdata or RDFa formats instead, which are not inspected here.

Why invalid JSON-LD is worse than no JSON-LD

It is worth stressing that a JSON-LD block that fails to parse is not simply "ignored gracefully" in every case — depending on how a particular crawler or validator handles malformed JSON, a single broken block can sometimes prevent otherwise valid structured data elsewhere on the page from being read correctly, and it always represents a wasted opportunity since the intended rich result will not be granted. Because structured data is typically generated automatically by a CMS, theme, or plugin rather than hand-written, it is easy for a template bug — an unescaped apostrophe in a product name, a price rendered without quotes, a locale-specific decimal separator — to silently corrupt every page that uses that template. Periodically re-validating JSON-LD after content or template changes catches these regressions before they accumulate across thousands of pages.
