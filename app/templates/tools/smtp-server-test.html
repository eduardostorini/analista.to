What is the SMTP Server Test?

This tool connects directly to port 25 of a domain's primary (lowest-priority) MX host and performs a read-only diagnostic conversation: it reads the server's opening banner, sends an EHLO command to see which ESMTP extensions the server advertises, and, if the server offers STARTTLS, attempts the TLS handshake to observe which protocol version and cipher suite are actually negotiated. The session then ends with a plain QUIT. At no point does this tool send MAIL FROM, RCPT TO, DATA, or any AUTH command — it never attempts to send mail, relay a message, or authenticate against the server. Only test mail servers you own or are explicitly authorized to test; connecting to a server you do not control to probe its configuration may violate its owner's acceptable use policy even when the probe itself is harmless and read-only.

How to interpret the result

A successful connection shows the raw banner the server presents to any connecting client (which often reveals the mail server software and version, useful context on its own), the full list of ESMTP capabilities it advertises such as SIZE (maximum accepted message size), PIPELINING, 8BITMIME, and — most importantly for security purposes — whether STARTTLS is present at all. If the server offers STARTTLS, this tool completes the handshake and reports the negotiated TLS protocol version and cipher suite, which reveals whether the server still permits outdated, weak protocol versions. A server without STARTTLS listed accepts only unencrypted plaintext delivery, meaning any mail sent to it travels the network path in the clear and can be read or altered in transit by anyone positioned on that path.

Common use cases

This tool is used by domain and mail server administrators to confirm that a newly deployed or reconfigured mail server actually advertises STARTTLS and negotiates a modern TLS version before relying on it to receive production mail, and to quickly check a server's banner and capability list without needing to open a manual telnet or openssl s_client session. It is also useful when investigating whether a legacy mail server on the domain's MX record list is holding back the domain's overall transport security — for example, a modern primary MX alongside a decades-old backup MX that still only accepts plaintext connections.

Limitations

This tool only tests the single MX host with the lowest priority number (the primary destination); a domain frequently has multiple MX records, and secondary or backup mail servers may be configured very differently — use the MX Lookup tool first to see the full list, and be aware other hosts in that list are not covered by a single run of this tool. It also cannot verify whether the certificate presented during the STARTTLS handshake is trusted by public certificate authorities in a way that blocks the connection outright — it reports the negotiated protocol and cipher regardless of certificate trust, since the goal is visibility into the transport configuration, not a pass/fail judgment on the certificate itself (use the SSL Certificate Checker for that, on a domain that serves HTTPS).

Why STARTTLS support matters

Even where a domain has not adopted stricter mechanisms like MTA-STS or DANE, simply offering STARTTLS with a reasonably modern TLS configuration is the baseline expectation for any mail server accepting production email in 2026 — its absence means every message delivered to that server, regardless of how carefully the sender protects its own infrastructure, crosses the network unencrypted. Because STARTTLS in the absence of MTA-STS is only opportunistic (a network attacker can strip the announcement before a client ever sees it, silently forcing a plaintext fallback), confirming STARTTLS is advertised is a necessary first step, but domains that handle sensitive mail should pair it with the MTA-STS Checker and TLS-RPT Checker tools to close the downgrade attack window entirely.
