What is DNS propagation?

DNS propagation is the process by which a change made to a domain's DNS records — a new A record pointing to a different server, an updated MX record for a mail migration, or a modified TXT record for a verification token — spreads across the thousands of independent recursive resolvers that internet service providers, corporate networks, and public DNS services around the world use to answer queries. DNS is a heavily cached, distributed system by design: every record has a time-to-live (TTL) value that tells resolvers how long they are allowed to keep answering from their local cache before they must ask the authoritative nameservers again. Because different resolvers cache the old value at different moments and with different TTLs, a single DNS change is never visible everywhere at once — it becomes visible gradually, resolver by resolver, as each one's cached copy of the record expires. This tool queries a fixed set of major public resolvers directly, bypassing your own device's DNS cache, so you can see exactly which of them are already serving the new value and which are still serving the old one.

How to interpret the result

Each row in the results table represents one independent public resolver — Google Public DNS, Cloudflare, Quad9, OpenDNS, Comodo Secure DNS, and Level3/CenturyLink — queried directly on port 53 with a short timeout. A resolver marked ok answered the query and returned the values shown; a resolver marked no_record answered but has no record of that type for the domain (which may be expected, or may indicate the record was removed); and a resolver marked error could not be reached or timed out within the query window, which is usually a transient network issue rather than a DNS problem. When every resolver that answered successfully agrees on the exact same set of values, the change is reported as "fully propagated." When resolvers disagree — some still returning the old value, others already returning the new one — the change is still "in progress," and you should expect full consistency once every resolver's cached TTL has expired.

Common use cases

This tool is most useful right after making a DNS change that needs to be visible globally before you can safely proceed with a dependent step: migrating a website to new hosting and waiting for the A record to point everywhere to the new server before decommissioning the old one, cutting over email delivery to a new provider by watching the MX record propagate before disabling the old mailboxes, or confirming a domain ownership verification TXT record has reached the resolver a third-party service will use to check it. It is also useful for diagnosing reports from users in different regions who claim to see different content or receive email inconsistently after a change — comparing the answers from resolvers with different countries of operation can reveal whether the discrepancy is a genuine propagation delay or a misconfiguration specific to one authoritative nameserver.

Limitations

This tool reflects the state of eight major public resolvers at the moment of the query, not the literally billions of resolver caches operated by every ISP and corporate network worldwide — some private resolvers may lag behind or ahead of the public ones shown here, particularly if they use unusually long negative-caching or minimum TTL overrides. A high TTL on the record being replaced will naturally slow down propagation regardless of what any checker reports, since resolvers are not required to discard a cached answer before its TTL expires. Results are cached briefly on our end to keep response times fast and avoid overloading the public resolvers with repeated identical queries, so re-running the check seconds apart may return the same cached result rather than a fresh one.

Reducing propagation delay before a change

The most effective way to make a future DNS change propagate quickly is to lower the TTL of the record well in advance — ideally 24 to 48 hours before the actual change — so that by the time you make the switch, resolvers worldwide are already refreshing that record frequently and will pick up the new value almost immediately. Making the change first and lowering the TTL afterward has no effect, because resolvers that already cached the old record at the old (long) TTL will keep serving it for the full duration regardless of what the TTL says in the new, not-yet-fetched record. Planning ahead this way is standard practice for any DNS cutover where downtime or inconsistency needs to be minimized.
