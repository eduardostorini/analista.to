What is a nameserver health check?

Every domain is delegated to a set of authoritative nameservers, listed in its NS records, and every one of those nameservers is supposed to be able to answer queries about the domain identically and reliably. In practice, this is not always true: a nameserver can be temporarily or permanently unreachable, misconfigured to not actually serve the zone it is delegated for (a condition known as "lame delegation"), or simply out of sync with the others because a recent zone update was pushed to some nameservers but not all of them. A Nameserver Health Check queries every nameserver listed for a domain directly and independently — bypassing any single resolver's cache — and compares how each one responds, which is the most direct way to catch these problems before they cause intermittent resolution failures for real users.

How to interpret the result

Each row in the results table represents one nameserver delegated for the domain. The "reachable" column shows whether that specific nameserver responded correctly to an SOA (Start of Authority) query, which every authoritative nameserver for a zone must be able to answer; a "No" here, combined with a status like timeout, no_nameservers, or no_answer, is a strong signal of a lame or broken delegation for that specific server. The "SOA serial" column shows the zone's version number as reported by each nameserver — a higher serial means a more recent version of the zone data. If all reachable nameservers report the same serial, the zone is fully synchronized; if serials differ, some nameservers are still serving an older version of the zone, which typically resolves itself once the zone transfer between the primary and secondary nameservers completes, but can also indicate a broken or stalled zone transfer if it persists.

Common use cases

DNS administrators run this check immediately after adding, removing, or migrating a nameserver to confirm the new one is correctly serving the zone and that the change has fully propagated across every delegated server, not just the primary one. It is also a standard step when diagnosing intermittent DNS resolution problems reported by only some users — since which nameserver answers a given query is effectively random from the resolver's perspective, a single lame nameserver among several healthy ones can cause a fraction of all queries to fail or return stale data, a pattern that is otherwise very difficult to reproduce and diagnose without checking each nameserver individually. Hosting providers and registrars use similar checks internally to monitor the health of secondary DNS services they offer, and security auditors use it to flag domains with a single point of failure (all nameservers on the same network or provider) or with unreachable or misconfigured delegations that could be exploited or that indicate neglected infrastructure.

Limitations

This check queries each nameserver's currently-resolved IP address at the moment of the request; if a nameserver hostname itself has no A record, it is reported as unresolvable rather than checked directly, since there is no IP address to query over IPv4 without resolving one first. A nameserver responding correctly to a single SOA query at one point in time does not guarantee it is consistently healthy — transient network issues, rate limiting on the nameserver, or a brief maintenance window can all cause a temporary failure that does not reflect the server's normal operating condition, so a single failed check is worth re-confirming before concluding a nameserver is permanently broken. This tool also does not verify IPv6 (AAAA) reachability for nameservers, only IPv4.

What causes SOA serial mismatches

In a standard DNS setup, one nameserver acts as the primary (holding the authoritative, editable copy of the zone) and the others act as secondaries that periodically pull updates from the primary via a zone transfer, governed by the refresh, retry, and expire intervals published in the zone's SOA record. A serial mismatch simply means one or more secondaries have not yet completed their next scheduled transfer since the last change — usually resolving itself within the configured refresh interval, often just a few minutes. A persistent mismatch that does not resolve after that interval has passed typically points to a firewall blocking zone transfer traffic between the primary and a secondary, an incorrect transfer configuration (such as an IP allowlist that was not updated), or a secondary nameserver that has stopped polling for updates entirely.
