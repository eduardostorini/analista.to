O que são cabeçalhos HTTP?

Toda resposta de um servidor web carrega, além do conteúdo da página, um conjunto de metadados chamados cabeçalhos HTTP (HTTP headers). Eles informam ao navegador (ou a qualquer cliente HTTP) coisas como o tipo de conteúdo retornado, se a resposta pode ser armazenada em cache e por quanto tempo, qual tecnologia de servidor está processando a requisição, se cookies devem ser definidos, e diversas diretivas de segurança. Esta ferramenta faz uma requisição à URL informada e lista todos os cabeçalhos retornados, destacando com uma cor diferente o código de status HTTP da resposta.

Como interpretar o resultado

O código de status no topo (200, 301, 404, 500 etc.) indica o resultado geral da requisição — 200 significa sucesso, códigos da faixa 3xx indicam redirecionamento (veja o Redirect Checker para acompanhar a cadeia completa), 4xx indica erro do lado do cliente (como página não encontrada) e 5xx indica erro no servidor. Entre os cabeçalhos, vale prestar atenção especial ao Server e X-Powered-By (podem revelar a tecnologia por trás do site), ao Cache-Control (define por quanto tempo navegadores e CDNs podem reutilizar a resposta sem buscar novamente no servidor), ao Content-Type (define como o conteúdo deve ser interpretado) e a cabeçalhos de segurança como Strict-Transport-Security e Content-Security-Policy — para uma análise dedicada e com pontuação desses últimos, use a ferramenta Security Headers.

Casos de uso comuns

Desenvolvedores usam esta ferramenta para depurar problemas de cache (por que uma página não está atualizando após um deploy, por exemplo), para confirmar que um cabeçalho customizado configurado no servidor ou CDN está realmente sendo enviado, e para investigar rapidamente a stack tecnológica de um site de terceiros antes de uma integração. Também é útil para confirmar o `Content-Type` correto de APIs e arquivos estáticos, um erro comum que pode quebrar o comportamento esperado no navegador.

Limitações

Os cabeçalhos podem variar entre requisições devido a balanceamento de carga, CDNs com múltiplos nós, ou personalização baseada em cookies/geolocalização — o resultado mostrado reflete apenas a resposta obtida no momento exato da consulta. Esta ferramenta usa o método GET com um User-Agent próprio e identificado; alguns servidores podem retornar cabeçalhos diferentes para outros métodos (HEAD, POST) ou para navegadores reais.

Cabeçalhos de cache em detalhe

Entre os cabeçalhos mais influentes na experiência do usuário está o Cache-Control, que aceita diretivas como max-age (por quantos segundos a resposta pode ser reaproveitada sem nova checagem), no-cache (permite guardar, mas exige revalidação a cada uso) e no-store (proíbe qualquer armazenamento). Um Cache-Control mal configurado é uma causa comum de dois problemas opostos: páginas que não atualizam para os visitantes mesmo após um deploy (cache agressivo demais) ou sites lentos que buscam o mesmo recurso repetidamente do servidor sem necessidade (cache ausente ou tempo de vida curto demais). Cabeçalhos como ETag e Last-Modified trabalham junto com o cache para permitir revalidação eficiente: o navegador pode perguntar "isso ainda é válido?" com uma requisição leve, em vez de baixar o conteúdo inteiro novamente quando nada mudou.

Cabeçalhos personalizados

É comum encontrar cabeçalhos prefixados com X-, uma convenção histórica ainda amplamente usada para identificar cabeçalhos não padronizados criados por uma aplicação, CDN ou balanceador específico, como X-Request-Id, útil para rastrear uma requisição em sistemas de log distribuídos, ou X-Cache, que indica se uma CDN serviu a resposta a partir do cache ou buscou novamente na origem. Esses cabeçalhos costumam ser valiosos durante depuração de performance e incidentes, revelando detalhes internos da infraestrutura que não apareceriam de outra forma.
