What are HTTP headers?

Every response from a web server carries, in addition to the page content, a set of metadata called HTTP headers. They inform the browser (or any HTTP client) about things like the type of content returned, whether and for how long the response can be cached, which server technology is processing the request, whether cookies should be set, and various security directives. This tool makes a request to the provided URL and lists all returned headers, highlighting the HTTP status code with a different color.

How to interpret the result

The status code at the top (200, 301, 404, 500, etc.) indicates the overall result of the request — 200 means success, codes in the 3xx range indicate redirection (see the Redirect Checker to follow the full chain), 4xx indicates a client-side error (like a page not found), and 5xx indicates a server-side error. Among the headers, pay special attention to Server and X-Powered-By (which can reveal the technology behind the site), to Cache-Control (defines how long browsers and CDNs can reuse the response without fetching again from the server), to Content-Type (defines how the content should be interpreted), and to security headers like Strict-Transport-Security and Content-Security-Policy — for a dedicated analysis and scoring of the latter, use the Security Headers tool.

Common use cases

Developers use this tool to debug cache issues (why a page is not updating after a deploy, for example), to confirm that a custom header configured on the server or CDN is actually being sent, and to quickly investigate the technology stack of a third-party site before an integration. It is also useful to confirm the correct Content-Type of APIs and static files, a common error that can break expected browser behavior.

Limitations

Headers can vary between requests due to load balancing, multi-node CDNs, or customization based on cookies/geolocation — the result shown reflects only the response obtained at the exact moment of the query. This tool uses the GET method with its own identified User-Agent; some servers may return different headers for other methods (HEAD, POST) or for real browsers.

Cache headers in detail

Among the most user-impactful headers is Cache-Control, which accepts directives like max-age (how many seconds the response can be reused without a new check), no-cache (allows storing but requires revalidation on each use), and no-store (prohibits any storage). A misconfigured Cache-Control is a common cause of two opposite problems: pages that do not update for visitors even after a deploy (too aggressive caching) or slow sites that fetch the same resource repeatedly from the server unnecessarily (absent cache or too short a time-to-live). Headers like ETag and Last-Modified work alongside cache to allow efficient revalidation: the browser can ask "is this still valid?" with a lightweight request instead of downloading the entire content again when nothing has changed.

Custom headers

It is common to encounter headers prefixed with X-, a historical convention still widely used to identify non-standardized headers created by an application, CDN, or specific load balancer, such as X-Request-Id, useful for tracing a request in distributed log systems, or X-Cache, which indicates whether a CDN served the response from cache or fetched again from the origin. These headers are often valuable during performance debugging and incident investigation, revealing internal infrastructure details that would otherwise not appear.
