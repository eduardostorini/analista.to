What is a Content-Security-Policy?

Content-Security-Policy (CSP) is an HTTP response header — or, less commonly, an equivalent <meta http-equiv="Content-Security-Policy"> tag in the page's HTML — that tells the browser exactly which origins are allowed to supply scripts, styles, images, fonts, frames, and other resources for a page. It is one of the most effective defenses against Cross-Site Scripting (XSS), because even if an attacker manages to inject a malicious <script> tag into a page, a well-configured CSP can prevent the browser from ever executing it, since the injected script's origin (or the fact that it is inline at all) will not match the allowed policy. This tool fetches the given URL, reads the CSP header and checks for an equivalent meta tag, parses every directive, and flags configurations known to significantly weaken the policy's protection.

How to interpret the result

Each directive restricts a specific type of resource — script-src for JavaScript, style-src for CSS, img-src for images, and so on — while default-src acts as the fallback for any directive that is not explicitly listed. This tool specifically flags three well-documented weaknesses: 'unsafe-inline', which allows inline <script> blocks and event handlers to run, defeating a large part of CSP's XSS protection; 'unsafe-eval', which permits the browser to execute strings as code via eval() and similar functions, a common vector for obfuscated malicious payloads; and a bare wildcard (*) in script-src or default-src, which allows loading executable code from literally any origin on the internet. It also flags the absence of a default-src fallback entirely, since without it, any resource type not explicitly restricted is left completely unrestricted by the policy.

Common use cases

Development and security teams use this tool to verify that a CSP rollout was actually deployed as intended in production, to review third-party or vendor pages before an integration, and to catch regressions where a previously strict policy was loosened (often temporarily, "just to fix a bug") and never tightened back up. It is also useful when auditing a site ahead of a security assessment, since a present-but-weak CSP can create a false sense of protection if not reviewed for these specific pitfalls.

Limitations

This tool parses the policy actually delivered by the server for the single URL requested; it does not execute the page or attempt to trigger a real XSS to validate enforcement, and it does not evaluate Content-Security-Policy-Report-Only as equivalent to an enforced policy (report-only policies log violations but do not block anything). A CSP can also legitimately vary by page or route on the same domain, so a single check does not guarantee every page shares the same policy.

Building a CSP without breaking the site

Because a strict CSP can silently break legitimate functionality — a forgotten analytics script domain, an inline style added by a third-party widget, a font served from a CDN not yet listed — the safest rollout path is to deploy the policy first as Content-Security-Policy-Report-Only, paired with a report-uri or report-to endpoint, and observe real violation reports from actual traffic before switching to full enforcement. This avoids the common failure mode of writing an overly permissive policy (or leaning on 'unsafe-inline' as a shortcut) just to get past initial testing, which then never gets revisited.

Nonces and hashes as an alternative to unsafe-inline

Modern CSP deployments avoid 'unsafe-inline' almost entirely by using per-request cryptographic nonces (a random token added to both the CSP header and each trusted <script nonce="..."> tag) or content hashes (a SHA-256 hash of a specific inline script's exact contents, listed directly in the policy). Both approaches let specific, known inline scripts run while still blocking any injected script an attacker adds, since the attacker cannot predict the nonce for a future request or produce content matching an allow-listed hash — achieving the flexibility of inline scripts without CSP's biggest historical weakness.
