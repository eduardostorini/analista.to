What is the Page Size Checker?

Page size matters because every kilobyte a browser downloads costs time, money, and battery. Search engines also use performance as a ranking signal, especially on mobile, where slow pages can be downgraded or buried under slower competitors. The Page Size Checker fetches any URL and reports the exact transfer size the server sends, along with the content type, encoding, server software, and cache hints it declares. It uses a lightweight HEAD request by default, so it measures what the server would send without downloading the full body unless the server refuses to answer HEAD. This makes it fast and safe to run against production sites without consuming much bandwidth or triggering rate limits.

How to interpret the result

The main number to watch is the transfer size in kilobytes or megabytes. As a rough rule of thumb, a simple HTML page should be under 100 KB, a typical modern marketing page often lands between 200 KB and 800 KB, and anything above a few megabytes for a single HTML document is a red flag that should be investigated. Content type tells you whether the server is sending HTML, JSON, XML, or something else; if you expected HTML but see JSON, the URL may be an API endpoint rather than a page. Content encoding shows whether the server compresses the response with gzip, Brotli, or nothing at all — compression can cut transfer size by 60% or more, so missing compression on text-based content is a common performance issue. Cache control and x-cache headers reveal whether the response is cacheable and whether a CDN or reverse proxy served it from cache, which affects both speed and repeat-visit experience.

Common use cases

SEO professionals use this tool during audits to identify pages that are unusually large for their content type, which often points to unoptimized images, embedded fonts, or inline scripts that should be deferred. Developers use it before and after a build to confirm that bundling, minification, and image compression actually reduced payload size. DevOps teams use it to verify that CDN and compression settings are working after a deployment or a cache flush. Support teams use it to answer client questions about why a page feels slow by pointing to concrete size numbers instead of vague guesses. Buyers use it during website due diligence to check whether a site's pages are reasonably sized or bloated with legacy scripts and unoptimized assets. It is also useful when debugging third-party embeds or analytics tags that silently add hundreds of kilobytes to a page without showing up in the main bundle.

Limitations

This tool measures only the initial HTML response, not the full page weight including images, CSS, JavaScript, fonts, and XHR/fetch requests. A page that reports 50 KB in this tool may still download several megabytes of assets once the browser parses the HTML and starts loading subresources. For a complete picture, use browser DevTools or a lab tool like Lighthouse. Some servers refuse HEAD requests or return a different size for HEAD than GET; in those cases the number may be inaccurate or missing. CDNs and reverse proxies may compress or vary the response by user agent, language, or geography, so the size you see from this tool may differ from what a real mobile browser on a different continent receives. Finally, this tool does not execute JavaScript, so it cannot measure client-side rendered content or dynamically injected assets; for single-page applications, the initial HTML size is only a small fraction of the total experience.
