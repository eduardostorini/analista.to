What is SSL Deep Test?

SSL Deep Test goes beyond a simple certificate check. It connects to the target domain on port 443 and performs two independent analyses: first, it retrieves and parses the TLS certificate presented by the server — issuer, validity window, and the exact list of domains it covers — reusing the same certificate-parsing logic as our SSL Certificate Checker. Second, and more importantly, it opens a separate TLS handshake for each protocol version defined by the TLS standard (TLS 1.0, 1.1, 1.2, and 1.3), forcing the client to offer only that single version each time, to determine precisely which ones the server is willing to negotiate. This is the same technique used by tools like SSL Labs to build a protocol support matrix, and it reveals configuration weaknesses that a single ordinary connection would never expose, because a normal browser or client always negotiates the newest protocol both sides support.

How to interpret the result

The certificate section works exactly like our SSL Certificate Checker: watch for expiration and for an untrusted chain, both of which trigger browser warnings for real visitors. The protocol support table is the distinguishing part of this report — each row shows whether the server accepted a full handshake using only that specific TLS version. TLS 1.0 and TLS 1.1 are deprecated by every major browser vendor and by the PCI Security Standards Council; if either shows as Supported, the server is still willing to fall back to protocols with known cryptographic weaknesses (such as BEAST and POODLE-adjacent issues) whenever an old or misconfigured client requests them. TLS 1.2 and TLS 1.3 supported is the expected, healthy baseline for a modern server — TLS 1.3 in particular removes an entire class of legacy cipher negotiation problems and reduces handshake latency.

Common use cases

Security teams run this test before a PCI-DSS or SOC 2 audit, since auditors specifically check for disabled legacy TLS versions on any host handling sensitive data. It is also used after a web server or load balancer configuration change (Nginx, Apache, HAProxy, or a managed load balancer) to confirm that a hardening change actually took effect on the live endpoint, rather than trusting the configuration file alone — configuration drift between what is written and what a server actually serves is a common source of unpleasant audit surprises. Finally, it is useful when investigating compatibility complaints from very old client software that may depend on a protocol version the server has since disabled.

Limitations

This tool reports protocol-version acceptance and the certificate seen on a normal port-443 connection; it does not attempt a full cipher-suite enumeration, does not test for specific named vulnerabilities (such as Heartbleed or ROBOT), and does not evaluate HTTP-level security headers — for that, use the dedicated Security Headers tool. Some servers apply different TLS policies based on Server Name Indication (SNI) or client IP reputation; this test uses the domain you provide as the SNI value, matching what a normal browser visit would present.

Disabling legacy TLS versions

If this report shows TLS 1.0 or TLS 1.1 as supported, the fix is almost always a short configuration change rather than a code change: most web servers and load balancers expose a directive to set a minimum TLS version (for example, ssl_protocols in Nginx or SSLProtocol in Apache). Before disabling old protocols in a customer-facing production environment, it is worth checking server-side access logs for the negotiated TLS version of recent connections, since a small fraction of very old operating systems and embedded devices may still depend on TLS 1.0 and would lose connectivity entirely once it is turned off — a trade-off that is, in nearly all modern contexts, worth making in favor of security.

Why protocol testing matters beyond the certificate

A perfectly valid, trusted certificate says nothing about which protocol versions the underlying TLS stack will accept — the two are configured and audited independently. A server can present an impeccable certificate from a trusted authority while still accepting decade-old protocol versions with documented cryptographic weaknesses, because certificate issuance and protocol negotiation are handled by different layers of the server stack. This is precisely the gap SSL Deep Test is built to close: a single report that covers both dimensions of TLS health, so neither is checked in isolation.
