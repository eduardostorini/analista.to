What is MTA-STS?

MTA-STS (Mail Transfer Agent Strict Transport Security, RFC 8461) is a mechanism that lets a domain require that any inbound SMTP mail delivery use TLS with a certificate that actually validates against the domain, instead of the plain "opportunistic" STARTTLS that most mail servers fall back to by default. Opportunistic TLS has a well-known weakness: an attacker positioned on the network path can simply strip the STARTTLS announcement from the plaintext SMTP conversation before it ever begins, silently downgrading the connection to unencrypted delivery — since STARTTLS was never a guarantee, receiving servers accept the downgrade without complaint. MTA-STS closes this gap by publishing two independent pieces of configuration: a DNS TXT record at _mta-sts.<domain> that announces a policy exists (and its version, via an id= tag that changes whenever the policy is updated), and an HTTPS-hosted policy file at https://mta-sts.<domain>/.well-known/mta-sts.txt that lists the actual mode and the exact set of MX hostnames authorized to receive mail for the domain. Because the policy file is fetched over HTTPS with normal certificate validation, an attacker who can only manipulate the SMTP path cannot forge or strip it.

How to interpret the result

This checker validates both halves independently. If no DNS record is found, MTA-STS is simply not enabled for the domain — sending servers have no way to know a strict policy is expected and will fall back to ordinary opportunistic TLS. If the DNS record exists, the tool fetches the policy file and reports its mode: enforce means other mail servers must refuse to deliver mail if they cannot establish a validated TLS connection to one of the listed MX hosts; testing means failures are reported (if TLS-RPT is also configured) but delivery still proceeds even on failure, intended as a safe rollout phase; none means the policy is defined but explicitly disabled, which is functionally equivalent to not having MTA-STS at all. A DNS record present without a reachable policy file is itself a misconfiguration worth flagging — it usually means the mta-sts subdomain's certificate is invalid, DNS for it is missing, or the file is not being served correctly.

Common use cases

This tool is used when rolling out MTA-STS for the first time, to confirm both the DNS record and the policy file are correctly published and mutually consistent before trusting that inbound mail delivery is actually protected. It is also useful when auditing a domain's mail security posture alongside SPF, DKIM and DMARC (which protect against sender spoofing but say nothing about transport encryption), and when diagnosing delivery complaints from senders who report TLS negotiation failures against a domain that recently changed its MX hosts without updating the corresponding mx: entries in the policy file.

Limitations

This tool reports what the domain currently publishes; it cannot tell you whether every sending mail server on the internet actually honors MTA-STS, since support depends on the sender implementing RFC 8461 (major providers like Gmail and Outlook do). It also does not verify that the MX hosts listed in the policy file match the domain's actual DNS MX records — that comparison is worth doing manually with the MX Lookup tool, since a stale policy file listing decommissioned mail servers can cause legitimate mail from MTA-STS-aware senders to be rejected outright.

MTA-STS and TLS-RPT work together

MTA-STS on its own is a one-way street: once enforcement is turned on, the domain owner has no visibility into connections that fail against the policy unless TLS-RPT (RFC 8460) is also configured, since sending servers only report failures back if a reporting address is published. For this reason, best practice is to deploy MTA-STS starting in testing mode together with a working TLS-RPT record, review the reports for a period to confirm no legitimate mail server is failing the TLS requirement, and only then switch to mode: enforce. Use the TLS-RPT Checker alongside this tool to confirm that reporting is actually in place before relying on enforce mode.
