What is CORS?

Cross-Origin Resource Sharing (CORS) is the browser mechanism that decides whether JavaScript running on one origin (say, https://app.example.com) is allowed to read the response of a request it made to a different origin (say, https://api.example.org). By default, browsers block this kind of cross-origin read under the same-origin policy; CORS is the standardized way for a server to explicitly opt back in, via response headers, and tell the browser which origins, methods, and headers it trusts. This tool sends a probe request to the URL you provide with a distinctive Origin header (https://cors-probe.analista.to, a domain we control and use only for this transparent test — not a spoofed or attacker-like value) and inspects exactly how the server responds.

How to interpret the result

If no Access-Control-Allow-Origin header is returned at all, the endpoint simply does not enable CORS for cross-origin JavaScript reads — this is the default, safe posture for most APIs that are not meant to be called directly from browser code on other sites. When the header is present, this tool checks for two well-known danger patterns. First, a wildcard (*) combined with Access-Control-Allow-Credentials: true is actually invalid per the Fetch/CORS specification and real browsers refuse to honor it — but its presence in server output is still a strong signal of a misconfiguration attempt, often from a framework default enabled without review. Second, and far more dangerous in practice, is a server that reflects whatever Origin it receives back verbatim in the response while also setting Allow-Credentials: true — this combination is valid per spec and browsers will honor it, meaning literally any website on the internet can make an authenticated, credentialed request to that endpoint on behalf of a visitor who is logged in, and read the response.

Common use cases

API and backend teams use this tool to verify that a CORS policy intended to allow only a specific set of trusted frontend origins was not accidentally implemented as a blanket origin-reflection pattern — a very common mistake in hand-rolled CORS middleware, since naive implementations often just echo back whatever Origin header the browser sent without checking it against an allowlist. It is also used during security reviews of third-party APIs before integrating with them, and to confirm that a public, unauthenticated API intentionally exposing itself with a wildcard origin is not also, by mistake, sending Allow-Credentials: true.

Limitations

This tool sends a single, simple GET probe with an Origin header — it does not send a CORS preflight (OPTIONS) request, so it will not show Access-Control-Allow-Methods or Access-Control-Allow-Headers values that a server only returns in response to a preflight for non-simple requests (such as those using custom headers or methods like PUT/DELETE). It also does not test authenticated requests with real cookies, since doing so would require a logged-in session specific to the target site, which this tool intentionally does not have or attempt to obtain.

Origin reflection versus a real allowlist

The safe way to support multiple trusted frontend origins is to maintain an explicit allowlist on the server and, for each incoming request, check the Origin header against that list before deciding what to send back in Access-Control-Allow-Origin — reflecting the exact matched origin only when it is found on the list, and omitting the header entirely otherwise. The dangerous shortcut this tool is built to catch is code that reflects any Origin unconditionally, which looks identical to a correct allowlist implementation in casual testing (since it "works" for the developer's own origin) but silently accepts requests from every other origin as well.

Why credentials change everything

Without credentials, a permissive CORS policy mostly just exposes data that is already public — a wildcard origin API serving read-only public data is a completely normal and intentional design. The moment Allow-Credentials: true enters the picture, cross-origin requests can carry the victim's cookies and browser-managed authentication state, turning a permissive origin policy into a direct path for any third-party site to act as the logged-in user against that API — which is why this specific combination is treated as a critical finding rather than a stylistic concern.
